A max-replica setting cannot turn either into durable local disk. These constraints rule out a lift-and-shift of the current security/finance/job databases, rather than ruling out those platforms after engineering the appropriate adapters.

[ACA ingress](https://learn.microsoft.com/en-us/azure/container-apps/ingress-overview) supports WebSockets/TLS, with a 240-second HTTP request timeout: create a durable job and poll; never digest a document in that HTTP lifetime. [ACA Jobs](https://learn.microsoft.com/en-us/azure/container-apps/jobs) supports finite tasks and configurable timeout/retry/parallelism. Its retry advice does not override the project's current no-automatic-paid-retry rule: configure zero replica retries until checkpoint/reconciliation proves a restart cannot duplicate a possible call. CPU-only scale rules are not a durable trigger for background work at zero replicas; use reviewed event/manual job dispatch or a nonzero worker baseline after shared-state engineering.

[WebJobs](https://learn.microsoft.com/en-us/azure/app-service/overview-webjobs) now supports Linux containers subject to image/runtime restrictions; this repository's Debian-based image is not Alpine, but actual supervisor/process integration still needs verification. [Always On](https://learn.microsoft.com/en-us/azure/app-service/configure-common) is required for continuous/cron WebJobs. Do not repeat outdated claims that Linux has no WebJobs or assume an HTTP-triggered background thread survives an app recycle. Plan/worker scale-out can multiply workers; use the same transactional fencing and provider limits.

## Hosting total cost of ownership across operating patterns

This supplements, rather than replaces, the three original cost scenarios below. All new numeric **rate** inputs remain UNVERIFIED. Official [ACA pricing](https://azure.microsoft.com/en-us/pricing/details/container-apps/) and [Linux App Service pricing](https://azure.microsoft.com/en-us/pricing/details/app-service/linux/) were accessed on **2026-11-13**, region planning **West Europe**, currency **USD**. Let `v` = suitable small-VM USD/hour; `d` = monthly OS+data disks; `b` = monthly coherent backup/snapshot cost; `n` = monthly private access/IP/networking; `l` = logs/monitoring/retention; `a` = registry/storage/pulls; `i_D` = inference envelope for D documents, using the explicit token formula below; `h_ops * r_eng` = operator/engineering time at an explicitly chosen value per hour. Define `F_vm = d+b+n+l+a` and `F_shared` = external transactional DB+canonical Blob+index service/disk+backup+network+registry+monitoring baseline for ACA/App Service. Optional Redis is additional to either when genuinely required; zero incremental Redis only means it is omitted, not that Azure Managed Redis is free.

For ACA define active app **plus job** vCPU-seconds `T_c`, GiB-seconds `T_m`, externally billable requests `Q`, exact active prices `c/m`, request price `q` per million, remaining subscription grants `G_c/G_m/G_q`, and separately eligible idle charge `I_idle`. Then `C_ACA = max(0,T_c-G_c)*c + max(0,T_m-G_m)*m + max(0,Q-G_q)/1e6*q + I_idle + F_shared + i_D`. Do not subtract each grant independently per application or assume other subscription workloads have not used it. [ACA billing](https://learn.microsoft.com/en-us/azure/container-apps/billing) gives grants of 180,000 vCPU-s, 360,000 GiB-s and two million requests per subscription/month, active versus eligible-idle billing, zero app resource charge at zero replicas and active-only job billing. A browser's open WebSocket, progress polling, CPU use or retained worker can prevent expected zero/idle behavior; estimate measured replica lifetimes, not query count alone.

For App Service let `s` = chosen suitable Linux plan USD/hour, `k` = instances, `w` = any separately billed worker capacity and `F_shared` as above. Conservative `C_App = 730*k*s + w + F_shared + i_D`. Sharing one plan between UI/API/compatible WebJob may reduce capacity duplication but not the external transactional-state requirement or aggregate memory peak. Ordinary app Stop does not release paid plan capacity ([plan management](https://learn.microsoft.com/en-us/azure/app-service/app-service-plan-manage)). **Current exception:** the official [10 November 2026 preview](https://azure.github.io/AppService/2026/11/10/app-service-plan-start-stop-public-preview.html) offers plan-level compute pause for eligible Premium v4/memory-optimized v4 tiers, not Basic, with plan-wide and scaling limitations; target eligibility/price/availability is UNVERIFIED. Do not claim App Service can never pause or assume that preview makes the smaller Basic plan scale-to-zero.

The aggregate ACA resource numbers illustrate the formula, not an actual feasible packaged allocation or measured requirement. UI, API, job and any vector/Redis containers need separate memory/CPU sums; 1 vCPU/4 GiB may be insufficient. `F_aks` includes at least disks, access/network, registry, monitoring/backup and optional managed dependencies; the detailed formula below provides its components. These are explicit UNVERIFIED input ranges; no current Azure SKU is claimed to cost them. The existing two-node reference's separate hypothetical USD 0.20–0.40/node-hour yields USD 8–16 for 20 hours or 292–584/month before its larger residual baseline. These are planning assumptions, not measurements/quotations and not new stages. Convert to TCO as `C_12months = setup_hours*r_eng + 12*(monthly_cloud + monthly_ops_hours*r_eng)`. Break-even for ACA is `migration_extra_cost < 12*(VM_monthly_cloud+VM_ops - ACA_monthly_cloud-ACA_ops)`. If the monthly savings term is nonpositive there is no positive annual cost payback. ACA zero replicas removes app resource charges, not external DB/Redis/vector host/Blob/log/registry/private-network charges or active jobs. App Service app stop retains plan charges except the distinct verified-eligible plan-stop mechanism; external services still remain. No option guarantees zero monthly total by stopping a container.

**Decision:** `AKS_NOT_REQUIRED`. Use the private single-VM candidate for the initial cost-conscious Azure deployment once local security/recovery/size and exact price gates pass. It retains the essential current document/governance correctness boundary with the least new infrastructure and migration. If the operator cannot accept single-host downtime or OS maintenance, record that changed requirement and re-evaluate ACA plus shared authorities; do not prematurely assert VM HA or choose AKS by habit. The future enterprise candidate is managed stateless apps/jobs plus durable shared services, not automatically AKS. No resources are activated by this recommendation.

## Distributed correctness requirements

Before C, all consumers of a provider quota must share one transactional admission policy/key and financial truth. Independent SQLite copies, periodic file synchronization or two network mounts do not provide it. Security release serialization presently uses a local SQLite transaction; distributed revocation requires a documented protocol, not eventual cache expiry presented as immediate denial.

| Shared fact | Required future property | Required integration/failure tests before multiple writers |
| --- | --- | --- |
| Ownership/principals/grants | Canonical issuer/tenant/subject, unique ownership, current role/disable epoch; deny cross-tenant lookup | Two hosts registering/sharing/revoking concurrently; role/key change and expired token at response release |
| Jobs/checkpoints/outbox | Admit idempotency + dependencies + outbox in one transaction; durable at-least-once dispatch | Duplicate/out-of-order delivery, send-before-mark crash, claim/commit races, DB restart/partition |
| Leases/fences/cancellation | Monotonic fencing epochs, server clock, atomic claim/cancel/commit; expired worker cannot publish | Worker paused beyond lease, new claim, old completion; cancellation concurrent with manifest write |
| Inference reservations and quotas | Atomic owner+tenant budgets and shared RPM/TPM/concurrency; one call identity executes at most once locally | Many simultaneous workers at exact limits; interactive/background contention; provider-start crash; network timeout and late usage |
| UNKNOWN obligations | Unsettled slots/cost remain reserved until independent reconciliation | Restore with STARTED/UNKNOWN, duplicate settlement, missing/contradictory provider usage; no budget reset |
| Publication/generation | CAS activation and rollback; immutable complete manifests; current generation/epoch checked at output | Two publishers, object/vector loss before/after activation, reader cutover, old-generation response release |
| Revocation/audit | Rollback never resurrects revoked access; bounded append-only audit fails closed | Revoke during inference/send, audit capacity/outage, multiple readers after restore |
| Backup/restore | Coherent authority/object checkpoint; financial/replay facts cannot roll back into free allowance | Disaster restore with stale index, tombstones/grants/consumed approval replay, missing object inventory; deny until reconciled |

These tests are future production gates. Stage 18.2 proves the local analogues only. No claim of globally exactly-once execution, invoice caps or production latency follows from local idempotency.
